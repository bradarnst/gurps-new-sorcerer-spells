# Plan: Simple Voice and Example Pass

## Recommendation

Use a separate script, but keep it deliberately simple.

Do one full run that:

- Reads `processed/final-spells.json`.
- Creates a timestamped backup copy before changing anything.
- Rewrites every spell's `description`.
- Fills every spell's `use_example`.
- Writes one complete output file at the end.
- Writes a small report with success/failure counts.

Do not add resumable cache files, source hashes, prompt hashes, worker queues, restart logic, or manual batch management for the first version.

The interruption risk is acceptable. If the run fails halfway, rerun it from the unchanged input or from the backup. This is much simpler and probably good enough.

## Separate Script

Add one new script:

- `tools/revoice_spells.py`

Keep the script focused on this phase only. It should not change taxonomy, spell IDs, costs, ranges, durations, statistics, keywords, or source lineage.

The script should only update:

- `description`
- `use_example`

## Inputs And Outputs

Input:

- `processed/final-spells.json`

Output, safest first run:

- `processed/final-voiced-spells.json`
- `processed/final-voiced-report.json`

After the output is reviewed, we can decide whether to overwrite/regenerate `processed/final-spells.json` or keep the voiced file as the new final artifact.

Backup:

- If the script is ever run in overwrite mode, first copy the existing target to a timestamped backup file.
- For the initial version, prefer writing a separate output file instead of overwriting. That makes backup logic almost unnecessary.

## Command Shape

Keep the CLI minimal:

```bash
python3 tools/revoice_spells.py
```

Optional arguments are fine if they stay minimal:

```bash
python3 tools/revoice_spells.py --input processed/final-spells.json --output processed/final-voiced-spells.json
```

Avoid adding `--limit`, `--resume`, `--force`, cache paths, or concurrency options in the first version.

## Generation Strategy

Use the user's full style prompt as a constant in the script or in one companion prompt file.

For each spell, send the model compact structured input containing:

- `spell_name`
- `spell_types`
- `keywords`
- `full_cost`
- `casting_roll`
- `range`
- `duration`
- current `description`
- `statistics`

Require strict JSON output:

```json
{
  "description": "...",
  "use_example": "..."
}
```

Prompt constraints:

- Preserve all mechanical facts.
- Do not invent new mechanics.
- Keep descriptions concise and table-usable.
- Make `use_example` a practical example of use at the table.
- Use the user's specific voice/style prompt.

## Validation

Before accepting each model result, check only the essentials:

- The response parses as JSON.
- `description` is present and nonblank.
- `use_example` is present and nonblank.
- No unexpected keys are required or inserted into the spell record.

After all spells are processed, write the output dataset and report.

Do not update `tools/build_spell_final.py` in the first implementation unless it blocks a needed validation step. The existing final builder currently expects blank `use_example`, so this new script can own validation for the voiced dataset until we decide the voiced dataset is the canonical final format.

## Failure Behavior

Keep failure handling simple:

- If one spell fails to produce valid JSON, stop the script with a clear error naming the spell.
- Keep the original input file untouched.
- Rerun the script after fixing the prompt/script issue.

This may lose progress from the failed run, but that is acceptable for simplicity.

## Suggested Implementation Steps

1. Add `tools/revoice_spells.py`.
2. Put the full style prompt in the script or a nearby prompt file.
3. Implement a simple loop over all spells.
4. For each spell, ask for `description` and `use_example` as strict JSON.
5. Validate the returned fields.
6. Write `processed/final-voiced-spells.json` only after all spells succeed.
7. Write `processed/final-voiced-report.json` with the processed count and any basic metadata.
8. Run once and review the output.

## Practical Answer

Use a separate script and write one complete output file at the end. Do not batch and do not checkpoint unless the first real run proves too slow or fragile. The simplest safe protection is to leave the original file untouched and write the revoiced result to a new file.
