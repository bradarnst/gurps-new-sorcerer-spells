# GURPS Sorcerer Spells Dataset Plan

## Objective
Build a definitive **Sorcery as Powers** spell dataset from `spells-raw.json` that is useful at the table, not just a mechanical mirror of source data.

Each spell record in the working set will have:
- normalized `spell_types` (array, multiple allowed),
- normalized `keywords` (array, multiple allowed; no `None`),
- unique game-ready description,
- `use_example` field present and blank for now.

## Confirmed Direction From Your Feedback
- We will **not** blindly recreate all 2207 spells.
- We will process the full source corpus first, then:
  - merge true redundancies,
  - keep meaningful variants,
  - identify and add missing high-value gaps.
- `Individual Spell` is treated as **untyped input noise** and must be fully retyped.
- `keywords` will be migrated to an **array**.
- The 24 standard colleges are a **minimum baseline**, not a hard cap.
- Type granularity should avoid oversized buckets; anything much above ~60 should usually be split unless the split would be artificial.

## Current Baseline Snapshot
- Source spells: **2207**
- Raw distinct type labels: **112** (fragmented/noisy)
- Empty descriptions: **477**
- Multi-type usage today: **0**

## Revised Execution Strategy
Use a **4-pass pipeline** with iterative checkpoints.

### Pass 1 - Canonical Taxonomy and Schema Migration
1. Define canonical `spell_types` framework:
   - Start from the 24 core colleges.
   - Add controlled secondary types where Sorcery utility needs them (cross-college or functional domains).
2. Define canonical keyword vocabulary (mechanical-first).
3. Migrate `keywords` to array format.
4. Add `use_example: ""` to all processed records.

### Pass 2 - Full Retyping and Description Rewrite (All 2207 Inputs)
1. Retype every spell from raw labels into canonical `spell_types`.
2. Assign normalized keyword arrays to every spell.
3. Rewrite descriptions uniquely while preserving rules fidelity.
4. Mark potential duplicates and near-duplicates during processing.

### Pass 3 - Consolidation (De-duplication and Variant Policy)
1. Collapse true duplicates/redundant spells.
2. Preserve distinct tactical/mechanical variants.
3. Produce a dedupe report with reasons for merge/keep decisions.

### Pass 4 - Gap Expansion
1. Analyze resulting taxonomy and gameplay coverage.
2. Add missing spells where there are practical play gaps.
3. Keep additions consistent with Sorcery-as-Powers costing and style.

## Batching Plan
- Pilot: **50 spells** to validate style/taxonomy.
- Wave 1: **200 spells**.
- Wave 2+: **300-500 spells** per wave once stable.

Reasoning: this still covers all source data, but controls rework risk while rules are being tuned.

## Type Granularity Rules (Updated)
- Target working range per type: roughly **12-60** spells.
- If a type grows above ~60, split by meaningful gameplay function unless the split is contrived.
- If a type is very small (<8), merge unless it has clear table identity.
- Multi-type tagging is encouraged when it improves discoverability.

## Keyword Rules (Updated)
- `keywords` is an **array only**.
- Replace `None` with meaningful tags.
- Keywords emphasize mechanics and table usage, e.g.:
  - delivery: `Melee`, `Missile`, `Jet`, `Area`, `Aura`, `Malediction`, `Touch`
  - resistance: `Resisted-HT`, `Resisted-Will`, `Resisted-DX`, `Unresisted`
  - role: `Buff`, `Debuff`, `Damage`, `Control`, `Defense`, `Information`, `Utility`, `Travel`, `Summoning`
  - behavior: `Persistent`, `Cyclic`, `Leveled`, `Obvious`, `No-Signature`

## Description Standard
Per spell description must:
- remain mechanically accurate to stats/cost/range/duration,
- be unique in wording,
- explain practical effect and tactical intent,
- read naturally for GM/player reference.

## QA Gates Per Iteration
- 100% canonical `spell_types` assigned (`Individual Spell` eliminated).
- 100% `keywords` arrays populated (no `None`).
- 0 blank descriptions in processed batch.
- duplicate/near-duplicate flags tracked.
- type distribution report produced (identify oversized/undersized types).

## Outputs Per Iteration
1. Updated spell batch.
2. Type distribution and candidate splits/merges.
3. Keyword distribution and outliers.
4. Duplicate/variant decision log.

## One Remaining Policy Decision Before Implementation
Decide how to represent merged redundancies:
- **Option A:** keep only one canonical spell record and remove duplicates.
- **Option B:** keep canonical record plus alias list (old names retained as references).

Recommended default: **Option B** during build (safer traceability), then optional pruning to Option A at finalization.
